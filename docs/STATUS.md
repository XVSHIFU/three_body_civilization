# 当前状态 · 2026-10-01实际浏览器低帧率已恢复，用户确认流畅

## 实际试玩窗口诊断（2026-10-01，最新）

版本844048d加临时开发采样；用户本人在本机Chrome走路、转视角。开启图形加速前使用Microsoft Basic Render Driver软件渲染，约10–12 FPS；用户开启图形加速并重启后，实际窗口使用RTX 4060 Laptop，连续样本约165 FPS，帧间隔p95约6.3ms。前后视口1468×970、绘制缓冲2202×1455、倍率1.5相同。这解释了开发者窗口流畅而用户窗口持续低帧率的差异。

本次已确认硬件渲染恢复和帧率提升；用户随后明确反馈“已经流畅了”，本轮走路和转视角卡顿反馈已关闭。这不作为完整性能矩阵或P2全部验收。临时诊断代码已收起，保留本地可恢复副本；不提交浏览器会话、原始采样或个人数据。游戏代码保持844048d，不继续降低画质或扩展范围。下面为先前优化及其当时结论。

## 最新用户反馈与修正（2026-10-01）

用户认为庭院画面可以接受，关闭／返回正常；但走路、转视角都不顺，类似画面衔接不上，体感明显不如MC。**美术与关闭返回已获认可，整体流畅度没有通过。** 不扩大庭院范围。

已修正已定位的问题：庭院原先每秒60次物理位置直接送到高刷新画面；现在复用原型PositionInterpolation，只平滑显示位置，碰撞、速度及物理步长不变。静态场景阴影不再每帧重算；阅读／暂停画面未变化时不重复提交WebGL绘制，隐藏标签也停止绘制；鼠标锁定状态切换重置插值以避免返回回弹。锁定已生效时不重复请求。

检查窗口1440×900、DPR 1、RTX 4060 Laptop、约165Hz：连续W键样本中位置不变帧从171/267降至2/268，行走终点一致；这衡量位置连续性，不是帧率提高。固定视点绘制调用91→59。2560×1440、渲染倍率1.6的脚本转视角样本，前后帧间隔p95约6.5／6.6ms，未复现用户的整体掉帧，因此**不能宣称整体卡顿已解决**；需要用户刷新实际浏览器复验。浏览器阅读暂停期间已观测到模拟和WebGL绘制计数都停止。

截图中的Esc条幅属于浏览器鼠标锁定UI。Pointer Lock接口没有控制该提示显示次数的选项；网页不能保证只显示一次。保留已认可的释放鼠标／主动点击恢复方式，没有用自绘光标或更改Esc行为规避提示。依据：[MDN接口参数](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestPointerLock)、[Chromium提示实现](https://chromium.googlesource.com/chromium/src/+/4a8573cb240df29b0e4d9820303538fb28e31d84/chrome/browser/ui/exclusive_access/exclusive_access_bubble.h)。

108项测试、类型、构建通过，Chrome庭院两项浏览器回归通过；已查看优化后的真实画面。下一步只复验走路／转视角的实际体感，不推进闭环或扩展。
